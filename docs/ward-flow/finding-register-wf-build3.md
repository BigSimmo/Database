# Finding register — WF-BUILD3 test sweeps

**Date:** 2026-09-02
**Source documents:**

- `docs/ward-flow/wf-build3-005-ts-test-sweep.md` (the "`.ts` sweep")
- `docs/ward-flow/wf-build3-004-dom-test-sweep.md` (the "DOM sweep")

**What this register is:** every individual finding these two documents recorded, pulled out into one
table, with each one rewritten in plain English. **Nothing has been triaged, ranked, or dropped.**
Deciding which of these are real problems worth fixing is a job for the project owner, not for this
extraction pass.

**What "TESTED" and "REASONED" mean here:** TESTED means the source document says somebody actually
made the change described and ran the tests to see what happened. REASONED means a person read the
code carefully and worked out what they believe would happen, but nobody actually ran it. REASONED is
not "weaker" or "less trustworthy" by itself — it just means the claim hasn't been put through a real
test yet. UNCLEAR is used only where the source document genuinely doesn't say which of the two it is.

**A mismatch this register cannot resolve, stated plainly rather than guessed at:** the `.ts` sweep
document itself reports several different totals for how many findings it contains — "129" in its
running-totals table, "131" in its own final summary, and "103" in a later section that explicitly
says it only covers 103 of "the 129 findings" and that 26 were never written down anywhere at all.
The document's own author says in the text, in these words, that the "131" figure was _"my own
count-from-memory error."_ My mechanical count of headings that actually follow the document's
`n.m` numbering pattern is **111**. I cannot reconcile 111, 129, 131, and 103 with each other, and
neither, by its own admission, could the document. I am reporting what I actually counted, not
picking whichever of the document's numbers looks closest.

**A methods note on what counts as a "numbered finding":** the brief asked for headings of the exact
form `## <n>. ` and `### <n>.<m> — `. The `.ts` document has **zero** headings of the first form. Of
the second form, most (95) are written exactly that way, but a further 13 carry a warning symbol (⚠️)
or a tick (✅) directly before the number — for example `### ⚠️ 2.5 — …`. These are clearly the same
running numbering scheme, just with an emphasis mark added, so I have included them rather than
dropping them on a technicality. I have also included two findings (15.1 and 15.2) that the document
labels the same way but writes as bold text inside a paragraph rather than as a true heading, because
they are explicitly introduced as "two findings" from a file the earlier sweep missed. All of this is
flagged so nobody mistakes my count for a stricter mechanical one than it is.

**Duplicate finding numbers, which is a defect in the source document, not in this extraction:** the
`.ts` sweep contains two unrelated batches of readings that were both numbered starting at "8.1" —
one covering `ward-flow-contracts.test.ts` and four other files, the other covering
`ward-legal-figure-guard.test.ts` and three other files. So "8.1" through "8.7" each refer to **two
different findings about two different files** in the source document. I have kept the document's own
numbers and added `(a)`/`(b)` suffixes purely so this register's rows can be told apart — `(a)` is the
`ward-flow-contracts.test.ts`-family batch, `(b)` is the `ward-legal-figure-guard.test.ts`-family
batch. This collision is also listed under "Flagged contradictions" below.

### Note on the two mutation-tested findings that turned out to be "guarded, but not by the test that claims it"

Three of the four TESTED entries above (9.9, 14.1, and 7.4) share an important shape: when somebody
actually made the change and ran it, the specific test named in the finding did **not** catch it —
but a _different_ safety mechanism (the automatic type-checking step, or another test file) did. The
document is explicit that this distinction matters: it is not the same as the property being
completely unprotected. Only **4.11** was tested and found to be genuinely unprotected by anything —
no test, and no type-check, catches it.

## 22. "Behind" and "stale" are different facts, and only one of them matters

**Found by measuring, not by reasoning.** Ward Builder Three, 2026-09-02, answering Ward Lead's
pre-fold status check. **Named as the transferable half by Ward Lead, who said it would not have
thought of it.**

**The question asked was "has your branch got master merged forward recently?" — and the honest
first answer was NO.** `git merge-base --is-ancestor d78a803f7 HEAD` returned false. Two ahead,
five behind. **Every session tonight, this one included, has read that as "you are built against a
world that has moved."**

**It does not mean that.** The next command settles it:

```
git diff --name-only HEAD...d78a803f7
docs/ward-flow/owner-open-questions-2026-09-02.md
docs/ward-flow/owner-wording-page-2026-09-02.md
docs/ward-flow/plan-to-finish-2026-09-02.md
```

**Three files, all documentation. So master's CODE is byte-identical to my merge-base**, and there
is no stale world in either direction — the five commits I lacked could not have changed a single
thing my code was built against.

⚠️ **BEING BEHIND IS A FACT ABOUT COMMITS. BEING STALE IS A FACT ABOUT CODE.** They come apart
constantly and the cheap ancestor check only measures the first. A branch can be fifty commits
behind and not stale at all; it can be one commit behind and completely stale. **The commit count
is not evidence about the thing anybody actually cares about.**

**Cost of getting it wrong in the safe direction:** an unnecessary merge, a moving branch, and — as
Ward Lead had already been bitten by once tonight — a fold that pulls in a commit nobody read.

## 23. An absence is exactly what somebody about to build expects to see

**Found by nearly making the mistake.** Ward Builder Three, 2026-09-02. **Ward Lead rated this above
either task it was attached to.**

**I had a task on my list: state the failing gate above the reason list on the coordinator override
form.** Before building it I grepped for the control — standard discipline, prove the task is still
outstanding. **The grep returned nothing. I very nearly took that as confirmation and built it.**

**The control already existed**, at `shortlist-panel.tsx:1383`, testid
`ward-shortlist-override-failing-gate`, rendering the unit name and the failing reason. **My grep had
used a testid I had misremembered from an earlier browser session — a name that has never existed in
that file.**

⚠️ **THE SHAPE: A SEARCH FOR THE THING YOU ARE ABOUT TO BUILD RETURNS EMPTY, AND EMPTY IS THE RESULT
THAT AUTHORISES YOU TO PROCEED.** A wrong search term and a genuinely absent feature produce
byte-identical output. **The confirming answer is the one that needs a second route, and it is
exactly the one nobody double-checks, because it agrees with the plan.**

**What it would have cost:** two override-reason controls on one screen, both looking correct, on a
clinical form. Ward Lead notes it nearly caused the same duplicate when it offered to build B2, and
that **on both occasions the only defence was somebody re-measuring rather than proceeding on a
memory.**

**The cheap fix that would have caught it:** search for the CONCEPT, not the identifier you recall —
`grep -n "override" <file>` returned all four testids in seconds and settled it immediately. **A
positive control on the search itself: if the file is meant to have override markup at all, an empty
result means the search is wrong, not the file.**
