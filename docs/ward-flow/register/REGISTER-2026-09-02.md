## What this is

This is a **list**, not a triage. The owner asked to see every finding that every Ward Flow
chat has produced so **he** can decide which ones are real, which ones matter, and what to do
about them. Nobody has filtered, ranked, merged, or dropped anything here — including findings
that a later message in the same source marked as retracted, withdrawn, or wrong. A register
that quietly removes what turned out to be wrong tells the reader nothing about how reliable the
rows that are left actually are, so those rows stay in, clearly marked.

This document assembles five source files that live on three different branches, groups every
finding under the chat and file it came from, and reproduces each source's own caveats about
itself verbatim, because several sources flagged real problems with their own reliability — a
false "mutation-verified" title, totals that cannot be reconciled, findings that were counted but
never written down, coverage limits, a diagnosis a source later found was its own error — and
those flags are the most valuable content here, not decoration around it.

## What the status column means

Four sources use a three-value STATUS column; a fifth source (Ward Builder One, Source E) adds a
fourth value of its own. This document keeps each source's own definitions rather than inventing
new ones:

- **TESTED** — a check **ran** that **would have failed if the claim were false**. This is not
  about confidence, and it is not the same as "I read the code carefully." It means something
  was executed — a test, a mutation, a page load — and the outcome depended on the claim being
  true.
- **REASONED** — someone read the code (or a document) and worked out a conclusion. Nothing was
  executed. A reasoned finding is not automatically a weak one; several of the most serious
  findings below are reasoned. It is an _unverified_ one, and more than one reasoned finding in
  this register turned out right in substance and wrong in mechanism.
- **OBSERVED** — somebody looked at the running screen, or at real output, and saw the thing
  directly.
- **REFUTED** — used only by Source E, in its own words: _"I asserted it, someone measured, and
  I was wrong."_ A refuted row is kept, not deleted, for the same reason a retracted row from any
  other source is kept: dropping what turned out wrong tells the reader nothing about how
  reliable what remains actually is.

Where a source's own column could not be reduced to a single one of these four values without
guessing — because the cell names two different values for two different things, or uses a word
outside this set entirely — that is stated explicitly as **UNCLASSIFIED** rather than forced into
a box. See the counting note below for exactly how that line was drawn, and where it was drawn
differently for two sources for a stated reason.

## Why there is no liveness column

This register deliberately does **not** re-check whether each finding still holds today. Re-
verifying roughly 230 findings before showing the owner any of them would itself be a triage —
just one performed silently, by deciding which findings survive long enough to be shown. Some
rows are already marked stale-closed, fixed, retracted, withdrawn, or refuted by their own
source; those markings are kept exactly as written, and are not proof of current state either.
Treat every row's freshness as of the date and commit stated in that row, not as of today.

## How the counting was done, and what it found

Counts below come from **parsing the STATUS column of each table row individually — one row,
one status** — not from a keyword search across the document text (a plain occurrence count of a
status word also matches that word in prose, headings, and explanatory notes, and overcounts).
That trap is not hypothetical: a first mechanical pass over Source E's status column, checking
only for the presence of the four known status words, would have silently counted a row reading
"REFUTED (mine) / TESTED (theirs)" as a clean TESTED, because the substring "TESTED" is present —
exactly folding a refutation into the wrong bucket while looking rigorous. The counts below were
produced by first listing the literal text of every status cell and classifying each by hand
against that text, precisely to avoid that failure mode.

**The rule applied uniformly across all five sources:** a row counts under one of the four named
values only when its status cell names exactly that one value (elaboration after a dash or comma
is fine — "TESTED, by mutation" is TESTED). A cell that names **two different** values — for two
different actors, two different aspects of the same finding, or a value and its correction — is
**not** resolved by picking the more favourable or more prominent one; it is reported as
UNCLASSIFIED, and listed by ID with the reason. A cell that uses a word outside the four-value
set entirely (for example "pending browser run" or "UNVERIFIABLE AS RECORDED") is UNCLASSIFIED
for the same reason.

**One exception exists, made once, on record, and not repeated here.** Source C's four compound
cells (V1, V6, V12, V13 — "REASONED by it; TESTED by Ward Builder Three" and similarly worded
rows) were resolved to TESTED in this register's first pass, on the reasoning that a named check
had actually run against that specific claim, which satisfies this register's own TESTED
definition. That resolution was reported to the owner as a discrepancy against Source C's own
self-report rather than a silent correction, and the owner's instruction on reviewing it was to
leave the disagreement standing rather than pick a side — not to redo the classification. It is
**not** extended to Source E's own compound cells below: Source E is a fresh source with no
equivalent sign-off, and applying the same resolution to it now would mean quietly deciding, on
this register's own authority, that "REFUTED (mine) / TESTED (theirs)" really means TESTED. That
is exactly the kind of judgement call this register exists to avoid making for the owner, so
Source E's compound cells are UNCLASSIFIED instead. The inconsistency between the two treatments
is real and is recorded here rather than smoothed over.

Two discrepancies carry over from the first assembly (Source C, unchanged) or are new this pass
(Source E); Source A's discrepancy has been retired. All three are detailed under the summary
table.
