## WL-026 — REFUTED, by me, against my own hypothesis: the Refer button does NOT lead to a form most users cannot submit

**I raised this as a suspected live defect on a screen the owner had just asked about. It is not one. Recorded because a hypothesis I raised loudly should be closed loudly, or somebody re-raises it in a week.**

**The hypothesis:** `RECEIVE_REFERRAL` is the only event that creates a referral, `EVENT_ROLE` permits exactly one role for it, so the Refer button leads to a form that rejects most users.

**Every hop confirmed except the one that decides it:**

```
1  person-screen.tsx:118  ->  /mockups/ward-flow/referrals/new     CONFIRMED
2  that route renders ReferralIntakeForm                            CONFIRMED
3  its submit dispatches RECEIVE_REFERRAL                           CONFIRMED
4  EVENT_ROLE.RECEIVE_REFERRAL = ["community"]  (one role)          CONFIRMED
5  a bad role returns a Rejection -- not silent, not thrown         CONFIRMED
6  WHERE DOES THE ROLE COME FROM?                        <- THE HINGE
```

⚠️ **HOP 6 KILLS IT. `role` in this codebase is not a live user attribute at all.** There is no role picker, no auth context, no role in the provider. **Every screen hardcodes the literal matching its own identity at each dispatch site** — the ED screen hardcodes `role: "ed"` at every one of its sites, and the intake form hardcodes `role: "community"`, which is exactly the one role permitted. **The gate is satisfied by construction and no runtime value can disagree.** The file's own header says so.

**Control, run and quoted rather than summarised:** `npx vitest run tests/ward-referral-screens.dom.test.tsx` → `Test Files 1 passed (1)` / `Tests 97 passed (97)`, 13.38s. Not refused by the coordinator. **And the coverage already exists both ways** — a success path and a real reducer refusal via a bad site code, asserting the rejection banner renders and no confirmation appears.

### ⚠️ WHAT THE REFUTATION LEAVES BEHIND, WHICH IS WORTH MORE THAN THE HYPOTHESIS WAS

**`role` is a BUILD-TIME TAG, not an identity.** It encodes _which screen is acting_, fixed in the source, and `EVENT_ROLE` therefore checks that a screen dispatches only its own events — a real property, and a useful one. ⚠️ **But it is NOT an access control, and nothing in the naming says so.** A reader who sees `EVENT_ROLE` and a rejection message reading _"requires role community, but was raised by role ed"_ will reasonably believe there is a permission model here. **There is a screen-identity model.**

**Not a defect and not owed work in a prototype** — recorded so that the day somebody adds real users, the difference is already written down rather than discovered by assuming the gate was already doing it.

**And the brief's own stop condition did its job:** the agent was told that if hop 6 showed the role hardcoded and correct it must say plainly there is no defect and stop, and not go looking for a different problem to justify the task. It stopped.
