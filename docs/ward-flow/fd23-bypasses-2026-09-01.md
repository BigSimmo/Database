# Two live FD-23 bypasses, and wiring the projection would close neither

**Swept 2026-09-01 at `a643464c5`, read-only.** Commissioned because Ward Verifier drew the
distinction nobody had: **unwired is not unexposed.**

The owner ruled that a ward may not see where else a patient has been referred. The module that
computes that projection — `ward-referral-visibility.ts` — reaches no screen. **The question was
whether that is dead code awaiting wiring, or a rule simply not applied.**

## ⚠️ The answer: a bypass exists, twice, and wiring closes neither

**Both leaks travel `Movement.referredUnitIds`. The projection module operates on `Referral`.**
Different field, different type. So connecting it produces **exactly the false assurance the sweep
was written to test for** — every guard would appear satisfied and both disclosures would remain.

**The rule is stricter than the summary anybody was working from.** `ward-referral-visibility.ts:19`
and ledger `FD-31`: a ward is told nothing about co-addressees, _"not their identities, and not that
they exist."_ An "also referred elsewhere" badge is named as forbidden, and **"the count is as
forbidden as the list."**

### Finding 1 — the navigation rail names the co-referred wards outright

`ward-role-switcher.tsx:78-80` reads `focusMovement.referredUnitIds` and renders each unit's **name**
under a group labelled "Ward", up to the cap of three. It is mounted by `ClinicalRail`, which
`ward-screen.tsx` mounts twice.

⚠️ **Three independent guards miss it, each for a different reason:**

- The structural boundary test computes ward-only modules as _ward graph minus shared graph_. The
  switcher is reachable from the allow-listed coordinator screen, **so it is subtracted out
  entirely. Any shared component is permanently outside that guard.**
- Its vocabulary regex covers `Referral` and `destinations` names. `referredUnitIds` is not in it.
- The FD-23 leak test asserts on the **card**, not the document — deliberately, per its own comment.

**The repository's own browser journey proves the reachability**: it refers a movement to three wards,
asserts the count, then opens the switcher. `focusMovementId` persists across role switches by design.

⚠️ **The irony is the finding.** The "Parallel referral" badge — which named _nowhere_ — was
deliberately removed from the card on the owner's 2026-08-31 ruling. **The rail names them outright
and always has.**

### Finding 2 — the patient workspace renders the count, and the winner

`ward-management-console.tsx:313` renders the accepting unit's **name** when accepted, and otherwise
`"{n} referred"`. Reachable from a ward screen with no URL typing: rail → Patient search → the link.

**It discloses the count, and on acceptance the accepting ward's name — the exact fact
`ward-screen.tsx` goes to considerable lengths to suppress in its own withdrawal block.**
Unconditional; no precondition at all.

### A question rather than a finding

`ed-screen.tsx:1328` renders `Referred to N unit(s)` and `Accepted at <name>`. FD-23 is ward-facing,
and the module says an ED-scoped projection **"is a product decision, not an implementer's."** But a
ward reaches that screen in one click.

## ⚠️ The structural fact underneath all of it: there is no role gating anywhere

No role type, no viewer state, no permission check — searches for `viewerRole`, `canSee`,
`isCoordinator`, `permission` return only prose. **"Role" means only which URL you are on**, and one
flat 14-item navigation list is rendered on every screen, so all 35 routes are one click from a ward
screen.

**A privacy rule enforced by which page you chose to open is not enforced.** The three designated
ward-facing files are genuinely well defended; that defence is simply not where the boundary is.

## What is clean

`ward-screen.tsx` is properly built — its projection narrows unit ids to this ward, and it
deliberately does not render a withdrawal reason because the reason names the winner. `ward-board.tsx`,
`ward-daily-sheet.tsx`, `person-screen.tsx`, the community screens and the officer screen: nothing.

**Fragile:** `person-screen.tsx` — the screen the documents call most FD-23-bound — appears in
_neither_ list in the boundary test, so the structural guard does not cover it at all. It rests
entirely on its own DOM test.

## Addendum — four more surfaces render co-referral data, and two do it INDIRECTLY

A second sweep, over the thirteen board-and-list surfaces a ward can reach, found four that render
per-patient co-referral information. **Two of them do not mention any of the forbidden field names
at all** — they call a shared helper that does.

- **`patient-search.tsx:282`** calls `destinationUnit(movement, units)`, which is
  `movement.acceptedUnitId ?? movement.referredUnitIds[0]`. So when nothing has been accepted yet,
  the table prints **the first co-referred ward's name as "the destination"**, with nothing marking
  it as one of several or as unaccepted.
- **`handover-page.tsx`** does the same in three separate places, via `handoverSnapshot()` and a
  direct `destinationUnit` call.
- `referral-board.tsx` renders every declined destination by name in its "Also refused" line.
- `referral-match.tsx` joins **every** destination into one sentence, and separately renders
  "Accepted at X".

⚠️ **THE METHODOLOGICAL POINT IS THE FINDING.** Both indirect cases are invisible to a per-file
search for `referredUnitIds`, `acceptedUnitId`, `destinations` or `withdrawnReferrals` — the file
names none of them. **They were found only by tracing every imported helper back to its definition.**
Any future sweep for this class that greps file-by-file will report those two as clean.

**Whether these four are FD-23 breaches depends on a question the app cannot answer.** The referral
board and the match screen are coordinator surfaces by intent, and patient search is explicitly
allow-listed as seeing everything. **But there is no role gating, so "coordinator surface" means only
"a page a ward can also open".** That is the same root as the two findings above, and it is why the
count of breaches cannot be settled without deciding what a viewer is.

**Two left undecided by the sweep, deliberately:** `referral-intake.tsx` renders a category-level
aggregate across all referrals of a kind, naming no patient and no unit; `live-tracker.tsx` renders
`acceptedUnitId` alone as a booked transport's destination. Both are arguably in scope and neither
is clear-cut.

**Seven of the thirteen are genuinely clean**, several of them only apparently so until their helpers
were traced — `ward-board.tsx` and `ward-daily-sheet.tsx` both carry a `destinations` prop that is
discharge REGIONS, an unrelated concept with a colliding name.

## A third route nobody had considered: refusal messages carry the other unit's name

`ward-flow-reducer.ts` interpolates a competing unit's **name** into the text of a refusal, in at
least five places. Verified at `:778`:

    `movement ${movement.id} is already accepted at ${already?.name ?? movement.acceptedUnitId};
     the referral to ${attemptedUnit?.name ?? event.unitId} was withdrawn`

Same shape at `:857` (`WITHDRAW_REFERRAL`), `:898` (`PULL_PATIENT`), `:2506` and `:2513`
(`RELEASE_PULL`).

**So when a losing ward's action is refused, the refusal explains itself by naming the ward that
won.** Every projection, every membership test and every leak test in this codebase guards what a
screen READS from the record. **None of them guards what the reducer SAYS when it says no.**

⚠️ **This is not a breach today, and the reason matters.** Refusals render only in
`coordinator/exception-drawer.tsx`, reached from `coordinator-screen.tsx` — a coordinator surface,
and the coordinator may see everything. **But that is the same defence as the four surfaces in the
addendum above: it holds only while "a coordinator surface" means something the app can enforce, and
with no role gating it means "a page a ward can also open".**

**Recorded as a route rather than a finding**, deliberately. It becomes a finding the moment a
refusal is surfaced to the actor whose dispatch was refused — which is the obvious next feature for
anyone improving error feedback, and nothing anywhere would flag it.

## ❌ RETRACTED — "three independent guards all miss the same shape"

Restore an interpolated withdrawal reason naming the receiving unit, and **all three stay green**:

- **`ward-withdrawal-reason-privacy.test.ts`** — its `not.toContain(unit.name)` **cannot fire.** The
  file's own first test pins every reason to `/^[a-z_]+$/` (verified at `:46`), and every unit name
  contains spaces and capitals. **The format guard makes the privacy guard unable to fail.**
- **`ward-flow-contracts.test.ts`** — its regex matches the WORDS "name", "address", "diagnosis". The
  historical leak it celebrates having fixed contains none of them.
- **`ward-withdraw-referral.test.ts`** — checks one field of a multi-field record, and that field is
  a snake_case enum.

⚠️ **THAT WAS FALSE AND I COMMITTED IT AS FACT. Verified here by opening the test:**
`tests/ward-withdrawal-reason-privacy.test.ts:154-190` drives the **real reducer** —
`REFER_TO_UNITS` then `ACCEPT_IN_PRINCIPLE` — and asserts
`expect(WITHDRAWAL_REASONS).toContain(entry.reason)` against a **closed two-member enum**. An
interpolated string is not a member. **It fails outright.** The criticism landed on a different test
in the same file; nobody read the one doing the work.

**What actually survives, verified: the unit-name check IS live and IS applied to every unit — but
`allUnits()` returns UNITS ONLY.** Nothing checks a **site name**, a **site code**, a **unit id** or
an **ED name**: `allUnits` appears 4 times in that file, site-name terms zero. **So a label reading
"Withdrawn — a bed was confirmed at Rockingham General Hospital" passes every assertion**, being a
genuine enum member containing no unit name. **A site-name leak is uncaught; a unit-name leak is not.**

**Three guards are individually weaker than they read. They do not share a hole.**

⚠️ **WHY THIS ONE WENT FURTHEST WRONG, WHICH IS THE PART WORTH KEEPING.** It was the finding that
COMPOSED. Three separate readers each reported a weak guard in a different file, and **three
independent reports of the same shape read as corroboration** — so it was promoted to the headline
for looking like a pattern rather than an item. **They were three readings of three files, none of
which had checked whether any OTHER file caught it. Corroboration between findings that share a blind
spot is not corroboration.**

**Also retracted from the same sweep: the bed-grid label swap is caught**, by a DOM test pinning the
value against a hard-coded literal rather than another call to the same function. **But the triage
sharpened it rather than clearing it:** the sibling held-beds test would NOT catch it — on its fixture
`available === held === 1` coincidentally, and its comparisons run against output from the same
swapped function. **The whole guard on that label pairing is one assertion, on one fixture. Change
that unit's allocatable figure and the last real guard goes quiet with nothing red.**

**What stands, and it is now the only one of the three: `sexDesignation` on the movement path.**
Genuinely unguarded — every test importing `ward-eligibility` and every caller of
`eligibleCandidatesAmong` checked individually, with a known-positive control firing first. It is a
PRODUCTION gap rather than a test gap, which is why no assertion could be red about it.

⚠️ **TWO OF THREE WRONG, BOTH TOWARD ALARM. Apply that rate to the other 126.** Treat every one as
_"a test that does not do its stated job"_ and none as _"a gap"_ until somebody runs the mutation. — and each reads as though it covers
the case. This is the strongest argument in the whole audit for the difference between _a property
being tested_ and _a property being testable_.

**⚠️ RETRACTED — I recorded that `coordinatorScopedReferral` has **no field-set allowlist at all** — the three-level allowlists that make that 1,397-line test file look
guarded cover only the ward projection. Delete `originSiteCode` from it and _"the coordinator may see
everything"_ becomes false with the whole file green, because the one test that touches it compares
the production expression to a call of the same function. **That was false and I checked it only after somebody ran the mutation.** The TYPE is the allowlist:
`CoordinatorScopedReferral` declares eleven required fields, `originSiteCode` among them, so dropping
one is `tsc` error TS2741 — verified here against a control. **The 1,397-line test file does stay
green, which is what was observed; the conclusion hung on it was wrong.**

**Correct size of the exposure:** `verify:cheap` runs typecheck and so does CI, **so a dropped field
cannot merge.** What it survives is the fast local loop — a bare vitest run — until a broader gate.
Not worth a duplicate runtime guard: re-asserting in vitest what `tsc` already proves buys the same
verdict twice, which this repository has an explicit rule against.

⚠️ **WHAT SURVIVES IS A DIFFERENT AND WORSE CLASS.** `suburb` is in **neither projection's type** —
zero occurrences in that file, against `originSiteCode` at four as the control. **So there is nothing
for `tsc` to enforce.** An enforcement gap is caught by a stronger gate; **a type-completeness gap is
caught by nothing, because the contract itself does not mention the field.** It stands against that
module's own comment saying the coordinator "may see everything", and it is a product question rather
than a defect.
