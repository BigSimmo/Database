### M20 · The worker's Python parsing stack (PyMuPDF, Pillow, pytesseract, docling) has no automated vulnerability signal: no pip ecosystem in Dependabot, Trivy exits 0 to the job log only, dependency-report covers npm only

`.github/dependabot.yml:3-65 (npm, github-actions, docker only); scripts/trivy-image-scan.mjs:118-119 (`--exit-code 0`) and :143 (summary to stdout only); .github/workflows/docker-image.yml:117-123 (`continue-on-error: true`, weekly); scripts/dependency-report.mjs:34 (npm only)` · security · **CONFIRMED** · safe_cleanup=false · lane L16 (L16-F2)

- **Defect:** worker/python/requirements.txt and eval/docling/requirements.txt are hash-locked (good) but nothing ever tells the owner that a pinned version has a published CVE. Dependabot has no `pip` entry, the Trivy image scan runs weekly with `--exit-code 0` inside a `continue-on-error` step and writes only to the run log, the fortnightly Dependency Report shells out to npm only, and no pip-audit exists anywhere in scripts, package.json, .github or docs.
- **Trigger:** A CVE is published against PyMuPDF/Pillow (both parse attacker-supplied uploaded PDFs/images in the ingestion worker).
- **Impact:** The clinical ingestion worker keeps parsing untrusted documents with a known-vulnerable library until someone happens to read a weekly job log. This is the one dependency surface that processes attacker-controlled input and the only one with no alerting path; SECURITY.md lists the worker as in scope.
- **Proof:** grep -rlE 'pip-audit|pip_audit' scripts package.json .github docs → no files; grep -nE 'pip|requirements|python' scripts/dependency-report.mjs → only an npm execFileSync at :34; trivy-image-scan.mjs:118 `--exit-code 0`; dependabot.yml has three `package-ecosystem` entries, none `pip`. Traced, not executed.
- **Fix sketch:** Add a `pip` Dependabot entry for `/worker/python` (and `/eval/docling`) with the hashed-lock regeneration documented in docs/worker-deploy-runbook.md, or add `pip-audit -r worker/python/requirements.txt` to the fortnightly Dependency Report so the rolling issue carries Python findings; optionally make the Trivy step publish a summary to the rolling issue instead of the log.
- **Skeptic (CONFIRMED):** Partial control exists and the finder's framing is accurate: Trivy does scan the built images (which contain the pip packages) but weekly, with --exit-code 0, inside continue-on-error, and the result reaches only the run log, so the 'Docker image build' entry in notify-ci-failure never fires for a Python CVE. No pip ecosystem in Dependabot and no pip-audit anywhere. The worker parses attacker-supplied PDFs/images, so an unalerted known-vulnerable parser is a genuine security-process gap; no clinician-facing wrong number, so Medium not High. Fix (Dependabot pip entry or pip-audit in the fortnightly report) touches no protected surface, though a pip bump must regenerate the hashed lock (check:worker-python-locks:static).
