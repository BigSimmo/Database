### M23 · check:migration-history reports merged-but-unapplied migrations as informational and exits 0, so the post-merge gate cannot prove application of objects the drift snapshot does not capture

`scripts/check-migration-history-alignment.ts:141-166 (localOnly printed as 'pending apply', only remoteOnly throws); AGENTS.md 'Supabase project safety' bullet 3 ('must complete with BOTH … green')` · process · **CONFIRMED** · safe_cleanup=false · lane L06 (L06-F2)

- **Defect:** The alignment script computes localOnly (versions in supabase/migrations absent from live history) and prints up to 30 of them under 'Local-only (pending apply)', but only remoteOnly triggers the throw. AGENTS.md makes 'check:drift AND check:migration-history green' the gate that a merged migration actually reached production, relying on check:drift for the schema effect. check:drift compares only views/tables/indexes/policies/triggers/functions/extensions/constraints/storage_buckets (scripts/check-drift.ts:131-155). A migration whose effects fall outside that inventory is therefore invisible to both halves when it fails to apply: pg_cron job rows (20260901033250 unschedules/reschedules the four privacy-retention purge jobs), COMMENT ON, ALTER DATABASE SET, data-only fixes, grants on non-public schemas (the same migration grants on schema cron).
- **Trigger:** A migration merges to main; the Supabase integration apply fails or is skipped (the failure class the whole drift programme exists for — 15 no-statements rows in #Q5JHBJ); live-drift.yml runs on the push.
- **Impact:** live-drift is green while the migration is unapplied. For 20260901033250 specifically, a failed apply on production would leave the retention jobs in whatever prior state they had and nothing in the repo would notice; the privacy-impact-assessment retention table (docs/privacy-impact-assessment.md:280-282) would then overstate the control.
- **Proof:** not executed — traced. scripts/check-migration-history-alignment.ts:156-163: `if (remoteOnly.length > 0) throw …` is the only failure path; lines 149-155 only log localOnly. scripts/check-drift.ts:143-155 comparedFields has no cron/comment/database-setting category; supabase/schema.sql contains no cron.schedule (grep returned nothing) so the manifest replay cannot carry those rows either.
- **Fix sketch:** In check-migration-history-alignment.ts, fail when localOnly.length > 0 unless an explicit `--allow-pending` flag is passed (the scheduled/dispatch runs after a merge should never see pending versions once the integration has applied them within ~34 s), and have live-drift.yml's routing step name the pending versions. Document in docs/database-drift-detection.md which effect classes are outside the inventory and rely on this history check.
- **Skeptic (CONFIRMED):** Reproduced from the script text: a merged-but-unapplied migration whose effects lie outside the drift inventory (pg_cron rows, grants on non-public schemas, COMMENT ON, data-only) is printed as 'pending apply' and exits 0, so 'BOTH green' does not prove application for that class. Medium process (the incident class this programme exists for; privacy-retention purge jobs are the concrete example). Fix caution: docs/audit/gate-consolidation-audit-2026-09-02.md:362 marks `check:migration-history` 'LOAD-BEARING, **never touch**' (it broke hosted Preview branching once); failing on localOnly could also fire spuriously if the push-triggered run starts before the integration's ~34 s apply, so any change needs the arbiter and an explicit allow flag, and AGENTS.md's 'BOTH green' wording is itself slightly over-claiming.
