The readiness endpoint (Railway healthcheck target, so it cannot be gated) executes `select id from import_batches limit 1` through the service-role client for any internet caller with no rate limit. Separately, an anonymous `GET /api/health?deep=1` sets `checks.supabase = "unauthorized"`, which flips `ready` to false and returns HTTP 503 `status: degraded` even when the service is healthy. **Impact:** Cheap query, but it is a free lever on Supabase connection/pool usage that bypasses every rate-limit bucket; the 503-on-unauthorized shape can make a healthy deployment look down to a mis-configured monitor. **Fix:** Return 401 (or 200 with the deep block omitted) for an unauthorized deep request instead of 503; consider a tiny in-memory per-IP throttle or a short result cache (e.g. 2 s) on the readiness probe. **Skeptic:** Both halves trace as described. The unauthenticated readiness DB probe is required by the Railway healthcheck and is deliberately detail-free; the 'free lever on Supabase pooling' impact is a runtime claim not established offline (one cheap `limit 1` select per hit, behind Railway).
