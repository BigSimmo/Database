### M15 · A plain `npm run test` collects the caring-contacts Postgres project and drops/recreates the `caring_contacts` schema whenever CARING_CONTACTS_DATABASE_URL is in the shell, with no loopback-host guard

`vitest.config.mts:7-11,142-150; scripts/test-environment.mjs:1-30; tests/helpers/caring-contacts-postgres.ts:75-77; tests/caring-contacts-migrations.test.ts:64-67; scripts/gate-receipts.mjs:309-316` · data-integrity · **CONFIRMED** · safe_cleanup=false · lane L14 (L14-F2)

- **Defect:** vitest.config.mts adds the `caring-contacts-db` project whenever `process.env.CARING_CONTACTS_DATABASE_URL` is non-empty; the node project excludes the two DB files only from itself. `offlineTestEnvironment` (which every `npm run test`, `test:coverage`, `test:focused` run passes through) scrubs 27 provider names but not this one, so the config comment 'the default offline `npm run test` never collects them' is only true when the variable is unset. The helper's `beforeAll` runs `drop schema if exists caring_contacts cascade` and re-applies migrations against whatever host the URL names; neither `caring-contacts/run-db-tests.mjs`, the helper, nor the two test files check for a loopback host. The gate-receipt key (`OUTCOME_AFFECTING_ENV_VARS`) also omits the variable, so a `vitest run` pass recorded with the DB project absent is reused as a pass when it is present, and vice versa.
- **Trigger:** A developer who exported CARING_CONTACTS_DATABASE_URL for `npm run caring-contacts:db:test` (the documented workflow) later runs `npm run test`, `verify:cheap` or `verify:pr-local` in the same shell; or points the variable at any shared/staging Postgres.
- **Impact:** Ordinary unit-gate runs silently become destructive database runs (schema drop + migration replay + truncation of caring-contact plan/patient/audit rows) against the named database, and a shared-hosted URL would be reached without any provider-boundary prompt. Receipts can then vouch for a run that never executed the RLS proofs. Nothing in the repo's live Supabase project is affected unless a user points the variable at it — but there is no guard stopping that.

[{ name: "caring-contacts-db" ...`; scripts/test-environment.mjs providerEnvironmentKeys list has no CARING_CONTACTS_DATABASE_URL; `rg -i "loopback|127.0.0.1|localhost"` over run-db-tests.mjs and both DB test files returns only the example string in the error message. Not executed — traced.
- **Fix sketch:** Scrub CARING_CONTACTS_DATABASE_URL in `offlineTestEnvironment` and have `caring-contacts/run-db-tests.mjs` re-inject it via an explicit override (or pass `--project=caring-contacts-db` only when a dedicated `CARING_CONTACTS_DB_TESTS=1` marker is set); add a loopback-host assertion in `caringContactsDatabaseUrl()`; add the variable to `OUTCOME_AFFECTING_ENV_VARS`; correct the config comment and docs/testing.md:13.
