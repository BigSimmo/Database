## Ruling 13 — the lazy route boundary, and what the evidence actually proves

Implemented in two layers, and it is worth being precise about which layer does the work.

1. **Module boundary (this is the layer that gives the guarantee).** Nothing outside
   `src/app/caring-contacts/` and `src/components/caring-contacts/workspace/` imports the
   workspace. The tools catalogue names it by **href string**, never by import, which is why
   `caring-contacts-routes.ts` is deliberately React-free. In the App Router each route
   downloads only the chunks in its own client-reference manifest, so a module the dashboard
   cannot reach is a chunk the dashboard cannot download.
2. **`next/dynamic` at the route boundary.** `page.tsx` loads the shell through
   `next/dynamic`. Next 16's lazy-loading guide states that dynamically importing a Server
   Component lazy-loads the Client Components beneath it — which is the workspace's entire
   client payload (one component).

**Evidence**, computed from the freshly built client-reference manifests with the same
attribution functions `check:bundle-budget` uses:

```
/caring-contacts chunk count: 29
/caring-contacts gzip bytes: 217569
exclusive-to-caring-contacts chunks: 2 gzip bytes: 2121
    app/caring-contacts/page-6f8fe06ecbe6ca7d.js 1665 gz
    app/caring-contacts/error-d08144e0e64239a5.js 456 gz
dashboard / chunk count: 28
dashboard chunks that are caring-contacts-exclusive: 0
```

The dashboard route `/` references **zero** chunks exclusive to the workspace. The other 27
of the workspace's 29 chunks are shared framework/app chunks every route already downloads.

Honest caveat: I cannot separate the contribution of layer 2 from layer 1 in this build,
because with only one client component in the workspace both produce the same manifest. The
`next/dynamic` boundary is therefore best described as _structural insurance for the screens
Tasks 16–18 add_, not as the thing that currently keeps the dashboard clean. Layer 1 is what
currently keeps it clean.

## The blocker — the design-system adoption contract

`npm run test` is **red**, on `tests/design-system-adoption.test.ts` only, with two failures
that are both this one issue:

```
 FAIL  tests/design-system-adoption.test.ts:1256
- []
+ [ "production page route is undeclared: src/app/caring-contacts/page.tsx" ]
```

`scripts/generate-design-system-adoption.mjs` requires every discovered production page route
to be owned by a surface in `docs/design-system/adoption-contract.json`. That much is
mechanical. The problem is what a surface declaration must contain:

- `checkAdoptionManifest` fails a surface declared `expectedShellState: "v2"` unless **all five**
  proof categories (`dark`, `forcedColours`, `compact320`, `print`, `browser`) are `passed`
  with evidence.
- The only other value, `"compatibility"`, is closed off by a committed assertion:
  `tests/design-system-adoption.test.ts:1160-1161` requires `declaredV2SurfaceCount` and
  `v2MountedSurfaceCount` to equal `surfaces.length` — i.e. every surface must be v2.
- `"not-applicable"` proof is permitted only for a statically redirect-only route.

So there is no status in the schema that says "declared, proof arriving in Task 19". To make
the suite green today I would have to declare `browser: passed` for a route with no Playwright
coverage at all — and Task 19 exists specifically to add
`tests/ui-caring-contacts-workspace.spec.ts`. I did not write that claim. Fabricating a
governance proof row on a suicide-prevention prototype is exactly the class of
cannot-fail check this repository has been burned by, and the alternative — editing the
assertion at line 1160 — is the one thing the task brief forbids absolutely.

**This needs your ruling.** The options as I see them:

1. **Declare it v2 with `passed` proof now, citing the same repo-wide suites every other
   surface cites.** Green immediately. Defensible on precedent: `favourites` cites
   `tests/ui-visual-baseline.spec.ts` for `browser`, and that suite visits six canonical
   screenshots which do not include `/favourites` either — so the repo's operative meaning of
   this field is already "the suite that governs the design system", not "a test that visits
   this route". Cost: the ledger carries an optimistic row for four tasks.
2. **Extend the contract schema with a `pending` disposition for a newly-added surface**, and
   have Task 19 flip it to `passed`. Honest and durable, but it changes a governed contract
   and the committed v2-count assertion, which is a design-system decision, not mine.
3. **Sequence it differently** — land Task 19's browser spec before or with the surface
   declaration.

I recommend option 1 with a `docs/outstanding-issues.md` entry that Task 19 must convert the
`browser` evidence to the real spec, because the alternative is a red suite under Tasks 16–19,
and a red suite for four tasks is its own hazard. But it is your call, not mine, so nothing is
declared until you say.

## The other thing you should rule on — the brief contradicts its own test

The brief's prose says the not-yet-built destinations should be "marked unavailable with a
stated reason, per the button-wiring convention" — which makes them `<button aria-disabled>`.
The brief's Step 1 test says the desktop `Workspace` nav must contain exactly four **links**
whose text is `Today, Patients, Schedule, Templates`, and the phone nav four links
`Today, Patients, Schedule, More`. A control cannot be both a link and an aria-disabled
button.

You told me the test files are authoritative and to use them verbatim, so I did. The
consequence is real and you should see it plainly:

- `Patients`, `Schedule` and `Templates` are ordinary `<Link>`s to routes **that do not exist
  yet**. Clicking one today gives the application's 404 page. Plan 2B builds them.
- The "stated reason" convention is honoured for the eleven **other** declared destinations
  (New plan, Team, Guidance, Reports, Service stop, Access trail, Workload, Reconciliation,
  Notifications, Training, Coverage), which render as aria-disabled buttons in a "More
  destinations" panel. That panel is also what the phone nav's `More` entry jumps to — an
  in-page fragment anchor, not a route, which is why it is a plain `<a href="#…">` and why the
  test's `a[href^='/']` sweep does not require `data-internal-link` on it.
- This means the brief's fourth test is **not** vacuous — there are eleven aria-disabled
  buttons for it to inspect. Had I put the unbuilt destinations nowhere, that test would have
  passed while asserting nothing, and I would have had to report it as decorative.

If you would rather not ship three links that 404, the smallest fix is three placeholder pages
under the shell (about fifteen lines each, plus site-map and codebase-index rows). I did not
add them because the brief says explicitly that only `today` ships a page in this plan, and
adding routes the plan did not anticipate is an escalation, not a silent decision.
