## Ruling [124] — no repository method

`buildScheduleRange` takes `readonly PlanRecord[]` — whatever `listPlans` released for the actor —
and does the rest itself. It calls no store. `listSendableContacts` is neither called nor changed.

**Where the derivation lives, and why.** The sealed domain, `src/lib/caring-contacts/`. Three of the
four rules it composes are already owned there — the window mapping (`./schedule`), the sendability
classification (`./model`), the plan lifecycle — and the fourth, that a plan's own state holds
sending, is a rule about the domain rather than about any screen. There will also be more than one
reader: this HTTP route publishes it, and Task 13's Server Component render will read the store
directly rather than call the service over its own network, exactly as `patients/page.tsx` does
beside `plans/route.ts`. Both readers must get the same answer, and the only way to guarantee that is
for there to be one answer. The argument is written into the module header.

## What the read answers

`buildScheduleRange(plans, fromCalendarDay, toCalendarDay)` returns
`{ ok: true; view } | { ok: false; reason }`. The view holds every day of the inclusive range, in
order, **including the days holding nothing** — the seven-day strip and the selected day come from
one call. A single day is the range `(day, day)`; there is deliberately no second entry point,
because two entry points would be two places for the grouping to be applied slightly differently.

Each `ScheduleDay` holds:

- **`windows`** — always all three approved windows, in the order they occur in a day, taken from
  `SENDING_PREFERENCE_OPTIONS` so neither the order nor the wording is restated here.
- **`outsideApprovedWindows`** — see "What Task 13 has to render that the mockup does not show".
- **`exceptions`** — the named-exceptions panel's contents.
- **`counts`** and **`disposition`**.

Each `ScheduleEntry` carries the plan, patient and contact identifiers, the cadence label, the
message type, the AWST day and instant it sends at, and four derived facts:

| Field              | What it says                                                                   |
| ------------------ | ------------------------------------------------------------------------------- |
| `sendability`      | `contactSendability(state)`, unmodified — the contact's own answer.             |
| `planHold`         | What the PLAN's state says: `planNotStarted`, `planPaused`, `planEnded`, null.  |
| `isDue`            | Still to send AND not held. The only entries the service will actually send.    |
| `notSendingReason` | `absorbedByFirstContact`, `suppressed`, `cancelled` or `missed`; otherwise null. |

## The plan-state gate

The filed defect on `listSendableContacts` is that it has none. This read has one, and it is not a
workaround for that surface — it is the rule stated where a schedule needs it. Neither `pausePlan`
nor `activatePlan` touches a contact, so a draft plan's contacts and a paused plan's contacts both
sit in `scheduled`. A read that asked only the contact would announce a plan nobody has started, and
a plan a coordinator deliberately paused, as work the service is about to do.

`planSendingHold` is an exhaustive switch over `PlanState` rather than a list of held states, so a
seventh plan state cannot default into "this plan is sending".

## Counts are derived

`ScheduleCounts` is `StoredContactSummary & { due, held, needsReview }`. The sent / still-to-send /
never-will arithmetic is `summariseStoredContacts`'s, unchanged and not re-implemented; what this
read adds is the split of `stillToSend` into the part the service will send and the part its own plan
is holding. The invariant is stated on the type and asserted in the suite:
**`due + held === stillToSend`**.

Nothing in the code or in this report states how many contacts a plan has. The absorbed-contact case
is asserted by deriving both sides from the plan under test: the entries carrying
`absorbedByFirstContact` must equal the planned entries the planner marked suppressed, and the due
entries must equal the day's entries less those.

## The empty-state distinction, one layer down

`ScheduleDayDisposition` has three values, and the first two are the ones that matter:

- `noContactsPlanned` — no contact falls on this day at all.
- `nothingDue` — contacts fall on this day and none of them is due.
- `contactsDue` — at least one is.

A day whose every contact was cancelled by a withdrawal reports `nothingDue` with
`counts.willNotBeSent` equal to `counts.total` and each entry naming `cancelled`; a day that was
never given a contact reports `noContactsPlanned` with a total of zero. An absorbed first contact
reports `absorbedByFirstContact`, which is the plan working as designed, and is kept apart from a
cancellation, which means something stopped it. All three are asserted.

## Ruling [125] — the trail

The read is recorded as `{ search, contactSchedule, "<from>:<to>" }`. Its own `AccessedObjectType`
member rather than the caseload's `plan`: recording it as `plan` would be defensible by provenance
and wrong by meaning, and with no `objectId` filter on the trail's query surface a shared member
would make a caseload read and a schedule read one undifferentiated stream. The `objectId` is the two
days that were read — identifier-shaped by construction, because the schema accepted only two AWST
calendar days before either could reach it.

`src/app/api/caring-contacts/access-trail/route.ts`'s `z.enum` is a hand copy of that union and
nothing in the build compared the two. `tests/caring-contacts-schedule-route.test.ts` now pins them
as the same set, in the same order, by parsing both files; every step of that parse throws rather
than comparing two empty lists. That closes the mechanism the filed issue describes, as a side effect
of this task — flagged rather than claimed, because the issue is not mine to close and a maintainer
should decide whether this pin is where the check belongs.

## What Task 13 gets

A `ScheduleRangeView` per call, either from `GET /api/caring-contacts/schedule?from=&to=` or — the
shape the other workspace screens use — by calling `buildScheduleRange` on an `auditedRead` of
`listPlans` inside the Server Component, with the same access identity the route records. It gets,
per day: the three windows with their approved wording and send times; a fourth group for contacts
moved off an approved send time; the named exceptions; the counts; and the disposition. Every entry
carries its own state, its plan's hold, whether it is due, and why it is not.

It releases **no patient identity**: `PlanRecord` carries none, so a row is keyed by the synthetic
`patientId` and a screen wanting names reads `listPatientNames`, which is audited in its own right.
That is asserted at both layers.

### What Task 13 has to render that the mockup does not show

**A contact can be scheduled at a time that is not one of the three approved send times.**
`moveContactWithinDay` accepts any hour and minute inside the approved 09:00–18:00 window and both
stores persist it, so 11:30 is an ordinary stored state. Nothing in this domain says which window a
moved contact then belongs to, and inventing a band (09:00–11:59 is "morning") would be a second copy
of the window mapping and a rule nobody approved. So `sendingPreferenceAt` matches the approved hour
**and** minute, and a contact matching neither is reported in `outsideApprovedWindows` rather than
filed under a window it has left. The approved design shows three window columns and no fourth group.
**This is a difference between the design and the types, recorded rather than resolved**; the owner
should say what that group is called on screen.

**A held contact is not an exception.** A draft plan whose first contact day has arrived, and a
paused plan's contacts, are reported as `held` and are not put in the named-exceptions panel. That is
a judgement, not a derivation: the approved design's exception panel is about transport, and adding
an operational category to it is a product decision. Task 13 has `counts.held` and each entry's
`planHold` if the owner wants them surfaced.

**Named exceptions** are the four provider outcomes that are not a delivery, plus `missed` — five
contact states, classified by an exhaustive switch so a new state cannot default into "not an
exception". They are taken OUT of their sending window rather than listed twice, because the design
keeps named exceptions separate from the routine window lists and a screen rendering both would
otherwise count one patient as two. The invariant is asserted: **every entry a day holds appears in
exactly one group.**

## Verification

### Boundary cases, written first

- **17:00 AWST on the last day of a month.** The early-evening send hour is the closest a real
  contact comes to a day boundary; the case pins it on the last day of August and pins the following
  day as holding nothing.
- **00:00 AWST.** Unreachable through `buildApprovedSchedule` — the approved window starts at 09:00 —
  so this record is assembled by hand and labelled defensive, with `planned.calendarDay` deliberately
  set to the UTC date. Both wrong answers are therefore available to the code, and it must choose
  neither: a contact is placed on the AWST day of its own `sendAt`, never on the calendar day
  recorded beside it and never on the UTC date.
- **A range across a month end.** Every day is enumerated, including the empty ones.

### The shared machine

Every heavy run queued behind other worktrees' leases; retries were on the refusal, never on a break.
Two operational notes, because both cost real time and one was my own defect:

1. My first gate wrapper retried on any output mentioning the lock **directory path** — which a run
   that merely WAITED for the lease also prints. It therefore discarded good runs and retried for
   ever. The corrected wrapper keys on the coordinator's own `acquireHeavyRunLock` /
   `ADMISSION_BUSY` markers. This is the "checks that cannot fail" shape pointed the other way: a
   wrapper that cannot succeed.
2. Killing that wrapper left its `vitest` child alive and stalled on a dead pipe, holding the
   exclusive lease at zero CPU. It was provably mine — the lease record named this worktree — and
   terminating it released the lease cleanly. Wrappers here should write to a **file**, never to a
   pipe a supervisor may close.

## Concerns

1. **The fourth group is a shape the approved design does not have.** `outsideApprovedWindows` exists
   because `moveContactWithinDay` makes it reachable. The owner has not seen it and it has no
   wording.
2. **"Named exception" is my definition.** Five contact states, derived by exhaustive switch so
   nothing can default in, but the choice of those five — in particular including `missed` — is a
   judgement about what a coordinator must act on, not a rule the domain already held.
3. **Held plans are excluded from that panel by the same kind of judgement.** A draft plan whose
   first contact day has passed may well be exactly what a coordinator needs to see.
4. **The range maximum is a bound I chose.** A month, so a month view is possible; the reason it
   exists at all is that the range arrives from a query string.
5. **`package.json` is a shared file.** Both suites were added to `test:cc-guards`, which is the line
   the other implementers are most likely to have edited too. A one-line conflict for the controller.
6. **In production a malformed query answers 400 while a well-formed one answers 404**, because the
   query is parsed before `readHandler`'s demo gate. That is the access-trail route's existing shape,
   followed deliberately rather than invented; it is a small existence signal and it is stated here
   so the choice is visible rather than inherited silently.
7. **M17 is unfalsifiable.** Recorded above rather than described as covered.
