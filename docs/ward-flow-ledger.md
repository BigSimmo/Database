# Ward Flow — the ledger

**One place to look.** Ward Flow carries 93 numbered decisions, eight specifications, a roadmap,
several handovers, and three sessions building at once. Its problem is not too few documents — it is
that the same kind of fact lives in several of them, so an item can be closed in one place and still
open in another. This file is the single home for the facts that cross documents: **identity,
status, and what is owed.**

Created 2026-08-29 after a design sweep found four bookkeeping faults, all of the same shape and all
invisible to every gate. Each rule below exists because of one of them.

**Verified against:** `claude/ward-flow-ward-board` @ `73f119f92` · `claude/ward-flow-phases-6-7-design`
@ `3b6bba3d3` · 2026-08-29 11:33 AWST. **Re-verify before acting on it.** Every handover in this
project has gone stale within hours; two went stale during the sweep that produced this file.

## The rules that keep this true

Eleven rules. Each is here because its absence caused an observed failure, named in brackets.

**Which ones are load-bearing.** Rules 10 and 11 were added last and have the most evidence behind
them: the duplication rule 10 prevents happened **twice in one day**, and the pinning failure rule 11
prevents happened **four times**. They are also the only two that caught anything _in practice_ —
neither the ledger nor the numbering rule detected either duplication. **A message did, both times.**
Read 10 and 11 first if you read nothing else.

1. **One fact, one home.** This ledger holds identity and status. **Reasoning lives in the
   specification and is never copied here.** A copy drifts, and then there are two answers and no way
   to tell which is current.

2. **Every decision has a globally unique ID**, namespaced by document: `MET-`, `P3-`, `P4-`, `P5-`,
   `P6-`, `P7-`, `P8-`, `WB-`, `WB-DB-`. Never cite a bare `D3`.
   _[Five different decisions are called D3, and every ID from D4 to D9 is used five times over. The
   sharpest demonstration is inside one file: the ward board spec cites bare `D3` four times for its
   own waitlist decision and three times for Phase 6's, so the same two characters mean two things in
   one document — in the very sentences written to stop someone reversing a decision back. A second
   session independently mis-cited "the referral/movement seam (D14)". That is Phase 7's D14; a reader
   following it arrives at the ward board's D14, "community team names are invented, one per region" —
   a real decision, plausibly related, and completely wrong for the sentence citing it.
   **Obviously-lost is self-correcting; plausibly-wrong is not.** (Example and framing contributed by
   the settings/process session, which found it in its own documents.)]_

3. **A new decision must state what it supersedes — even when the answer is "nothing" — and the
   superseded entry must be updated in the same edit.** Not the next one.
   _[WB-DB-10 says the frozen on-screen view stays; WB-DB-11 deletes it. Neither marks the other, and
   WB-DB-11's only reference to WB-DB-10 tells the implementer to build them together.]_

4. **A question escalated to the owner is registered here the moment it is escalated**, before the
   session that raised it does anything else.
   _[A free-text field was escalated on 2026-08-25 with its measurement attached, then appeared on no
   list at all for four days.]_

5. **An answered question moves to the decision register and names the decision that closed it.** It
   is never merely ticked, and never left in place.
   _[The handover listed the receiving-time options as owed for ninety minutes after WB-DB-14 had
   answered them.]_

6. **A refusal is recorded with its reason.** A refusal with no reason attached gets reversed by the
   next person who finds it inconvenient. _(Existing roadmap principle, promoted to a rule.)_

7. **Cite by ID, and quote the decision's own words when reversing one.** If the words you quoted do
   not appear in the decision you cited, you have cited the wrong decision.
   _[WB-DB-10 and WB-DB-11 originally cited "Phase 6's D3". P6-D3 is the five-figure vocabulary rule;
   the frozen view is P6-D5 and P6-D6. The ward board session corrected the operative sentence in
   `cb6a86fe2` — it now reads "This reverses Phase 6's D5 and D6 outright" — within minutes of the
   finding. **This ledger's first version overstated the consequence**, claiming an implementer might
   delete the bed-figure vocabulary rule. WB-DB-11's title and its item 2 name `MorningView`,
   `FrozenMorning` and `morningHandoverInstant` explicitly, so the correct target was always in front
   of them. Correction raised by the Phase 8 session and verified against git history. One
   explanatory line inside WB-DB-11 still mis-cites D3 — see B2.]_

8. **This ledger reports; it never decides.** Nothing here is authority to change a specification, and
   no agent may alter an owner-approved list. Where this file and a spec disagree, **the spec wins and
   this file is wrong** — fix it here.

9. **One session assigns every decision number; nobody else.** Decisions are still made anywhere and
   their reasoning still lives in the specifications — but the ID comes from one place, which makes a
   collision impossible rather than merely unlikely. **Before opening any numbered series, check
   whether the project already has one.** That is the whole rule compressed, and it is the step that
   was skipped.
   _[Two decision registers existed by 2026-08-29 and neither session knew. The second was not created
   by a decision to create one — it was written in its own document's natural format, given a natural
   prefix, and numbered from one. It announced itself to nobody, including its author, until a sweep
   found it. Every other fault this project guards against eventually announces itself: a red test, a
   conflict, a figure that disagrees. A second register produces no symptom until someone looks, and
   nobody looks for a thing they do not know exists.]_

10. **Announce what you just wrote, immediately, in enough detail that another session can recognise
    its own document in the description.** Not a summary of intent — the actual section headings and
    the claim each makes. This is the only defence that has demonstrably worked.
    *[Two sessions independently wrote the same method document for the clinician check — four
    sections identical under different names. Earlier the same day, two sessions independently
    created decision registers. **The second duplication was written by the session that had authored
    the rule against it that morning**, which is what shows it is not carelessness: a session working
    alone with a clear idea writes the natural document for that idea, and the idea supplies no signal
    that anyone else is having it. Neither the ledger nor rule 9 caught either one. A message caught
    both.

    **A fifth instance, and it is the strongest: on 2026-08-29 a convergence would have excluded a
    live rewrite of the ward board. Neither the ledger, nor the numbering rule, nor `merge-tree`
    caught it — every mechanism in the repository said proceed. What stopped it was one session
    asking "do you want me to run it now, or wait?" rather than picking an interpretation.** The
    defence is not a document. It is declining to guess at another session's intent.]*

11. **Pin every claim to WHEN, WHERE and WHICH ARTEFACT.** A quotation gets a commit. A count gets a
    branch. A statement about a rule gets the config, not the documentation about the config.
    _[Four times on 2026-08-29 two sessions disagreed about a plain fact and both were right. One had
    read a spec before it was corrected and one after. One counted routes on its own branch and one on
    another — both found 21 and they were not the same 21. One read what the docs say about the
    button-wiring rule and one read `eslint.config.mjs`. One read a branch tip while the other
    described its own uncommitted working tree. **Every one presented as a disagreement about fact.**]_

    **THE OPERATIONAL FORM, and it is the most useful sentence in this file: PREFER THE CHECK THAT
    CANNOT BE NARROWER THAN THE QUESTION.** `git rev-list --count` over a self-report. Blob identity
    over `git status`. `find` over `ls`. **Reading the passage over grepping for the phrase you
    expect to find in it.**
    _[Three instances in one day from the Phase 8 session, all of them its own verification being
    narrower than its question, and all AFTER it had spent the day cataloguing that failure in others:
    `grep "22 unit"` returned nothing on a file containing **"22 inpatient units"**, and it told
    another session on that basis that the file was clear; `ls` reported **zero** files preserved
    after moving 66, because every name begins with a dot, and it nearly reported a data loss that had
    not happened; `grep "never leaves that screen"` returned nothing on text where that sentence
    **wraps across two lines**, and it nearly reported a decision's load-bearing reasoning as dropped
    from a paste. **Two false negatives and one false alarm, and nothing in any output distinguished
    them from a real result.**]_

    **The sharper form, reached independently by two sessions on 2026-08-29: a record of INTENT is not
    a record of OUTCOME.** Both read the session store's branch field — which records where a session
    _believes_ it is, snapshotted at session start — and warned a third that its work might be
    stranded on an empty auto-created branch. Nothing was stranded. The store was stale bookkeeping,
    not a live read.

    **And the method error outlives the non-finding.** The question asked was "which branch does this
    session think it is on", answered by `git rev-parse --abbrev-ref HEAD` and requiring every session
    to self-report. The question that settled it was "has anything ever landed on a suffixed branch",
    answered outright, for every branch at once, needing nobody's cooperation:

    ```bash
    git rev-list --count origin/main..<branch>    # 0 = nothing has ever landed there
    ```

    **Prefer the question that settles it over the question you can most easily ask.** Three sessions
    were asked to check something one command answered — and three self-reports still leave you
    inferring. This is the same shape as the `merge-tree` lesson above: a record of what someone
    means, read as a record of what happened.

12. **A CHECK THAT PICKS ONE CANDIDATE CAN NEVER REPORT THAT IT PICKED THE WRONG ONE.** `head -1`,
    `| head`, "the first match", "the obvious file" — every one of them silently discards the
    alternatives and returns a confident answer about a thing you did not ask about. **There is no
    error, no empty result and no ambiguity marker. The output of the wrong file is shaped exactly
    like the output of the right one.**
    _[2026-08-30. The board session reported a correction had reached the working line and gave its
    evidence: `grep -c "CORRECTED AGAIN"` → 1. This session re-ran it, got **0 on every branch**, and
    was composing a message telling a peer its verified claim was false. The file selector was
    `grep "superpowers/plans.*2026-08-29" | head -1` — and **two** files match that pattern. The one
    it took, `2026-08-29-ward-flow-referral-front-door.md`, sorts first and **was added by
    `4ef1f7098`, the very commit under examination.** So landing the fix is what caused the check
    for the fix to read the wrong file. Nothing in the `0` distinguished it from a real `0`.]_

    **This is the registry's branch-name trap in general form, and that is the argument for the rule.**
    That warning enumerated three `ward-board*` branches and asked which was live; once the live
    branch left the family the check could not say so, and returned a confident wrong answer to every
    session that ran it. **A check phrased as "which of these is it?" has no way to answer "none of
    them", and a check phrased as "take the first" has no way to answer "there were two".** Same
    defect, one in prose and one in a shell pipeline.

    **The operational form:** when a pattern selects a file, **print every match before you use one.**
    If the count is not 1, the question is not yet asked properly. `git ls-tree | grep <pat>` on its
    own line, then choose — never `| head -1` inside the command whose answer you intend to quote.

**The decision index in section C is derived, never hand-maintained.** Regenerate it rather than
editing it; the command is at the foot of this file.

## A. Mission

### The foundation — above everything else in this file

> **"The core principle is patient flow from the emergency department to the wards. That is the
> foundation. Everything is built on it."** — owner, 2026-08-29, said twice unprompted.

**Deliberately given NO decision number.** It is the frame this register sits inside, not an entry in
it — a numbered decision can be superseded by another numbered decision, and this one cannot be. That
is the judgement of the session that reported it and of the session that owns identity, recorded here
so the absence of a number reads as a choice rather than an oversight.

**The test every task, refusal and scope decision is subordinate to:** _does this help a person get
from an emergency department to a ward, or help someone see why that is not happening?_ If the honest
answer is no, it is decoration, and decoration goes last or not at all.

**How this changes the reading of group D's principles.** A refusal that would obstruct the forward
flow is the thing to re-examine, not the flow. That is **not** a licence to weaken them — the safety
and privacy principles stand, and none of them obstructs anything. It is a tie-break for a case
nobody has met yet, recorded now while it is cheap rather than argued out later under pressure.

**Discharge is in scope for a narrower reason than it was being given.** The reporting session had
been elevating discharge on the argument that beds come from discharge and only one side of the
equation is managed. That argument is true, and it is a _consequence_ of the foundation rather than
the foundation — treating it as the premise was quietly reshaping the plan's priorities. The correct
reason is that **discharge makes the forward flow repeatable**: someone leaves, a bed appears, the
next person moves into it. A demonstration where the bed never comes back shows one patient moving
once and then stops. That is the whole of why it is built early.

**The canonical mission is `docs/ward-flow-mission-and-refusals.md` on `claude/Wardquestions`
(APPROVED FRAME, 2026-08-29). It is not summarised here and it is not copied here.**

This ledger's first version carried its own three-paragraph summary. That has been deleted rather
than improved, and the reason is worth keeping: **two versions of the mission is the same fault as two
decision registers, and worse.** The mission is the one artefact whose exact wording _is_ the
product — every sentence was chosen against a specific room and a specific pushback, and that
document has a section explaining why each paragraph is there so nobody edits one out by accident. A
summary silently loses the reasons, and a reader who finds the summary first never learns a stronger
version exists.

The nine operating constraints are in `docs/ward-flow-handover-2026-08-29.md` §5. The two broken most
easily: **never invent a figure from the Mental Health Act, anywhere**; and **every bed dimension asks
"does this bed accept this person", never an equality** — an equality excludes every undesignated bed,
which is most of the network, and looks entirely reasonable in review.

### DECIDED is not IMPLEMENTED, and this ledger did not distinguish them

**Every decision row now carries one of two states.** `DECIDED` means the owner ruled and it is
written down. `IMPLEMENTED` means code changed. **This ledger conflated them until 2026-08-29 and
was wrong about at least one decision as a result.**

**The case that forced it — `WB-DB-11`, dropping the morning page's frozen view.** Commit
`e43f3f8f8`, message _"Ward board: the frozen morning view is dropped, everything is live (DB-11)"_.
`git show --stat`: **37 insertions, one design document, no code.** On the live branch the morning
page still holds `useState<FrozenMorning>` and `useState<MorningView>("fixed")` — **the freeze is
present and is still the DEFAULT view.** Verified here, not relayed.

**The transferable rule: a commit that RECORDS a decision has the same message shape as one that
IMPLEMENTS it.** `e43f3f8f8` is entirely truthful about its own subject — the decision _was_ made,
and the message describes it accurately. **`git log` proves a decision exists; only `git show --stat`
or the file itself proves anything shipped.** Found by the settings session auditing its own plan
against the code, which had recorded the freeze as already gone on the strength of that message.

**Its three siblings are UNVERIFIED, and my check was too weak to settle them.** `WB-DB-7`,
`WB-DB-10` and `WB-DB-12` were all decided "at the fold". Grepping for guessed symbol names returned
"no sign" for two — **which is exactly the narrower-than-the-question failure rule 11 names, so I am
recording it as unverified rather than as a finding.** Someone should check them properly, by reading
the morning page rather than searching it for names I invented.

### Every row is one of two types, and they need OPPOSITE maintenance

**A document states either a fact about NOW or a record of what was true THEN.** Correct the first.
**Date the second and never back-date it** — back-dating destroys the provenance that caught a
handover instructing a reader to undo a decision the owner had made nine hours earlier.

**This supersedes and explains the conditional convention below, which was the special case.** A
conditional row is not a _weaker_ record; it is a **correctly-typed** one. **A row asserting a
measurement without its date is a TYPE ERROR, not merely a risk** — and that is a stronger statement,
because a discipline ("remember to mark this one") fails quietly while a malformed row can be
recognised on sight. _(Framing contributed by the settings/process session, which is right that it
subsumes the convention.)_

### Decisions conditional on a measurement

Some decisions are correct _because of a number_, and the number moves. Marking them
`CONDITIONAL` puts the measurement, its timestamp and the command to re-take it in the row, so a
reader in three weeks sees that the basis has aged rather than reading a stale measurement as a
standing fact. **A decision that quietly stops being true is worse than one that was wrong from the
start — the wrong one gets argued with.** _(Convention proposed by the settings/process session.)_

**`PROC-3` — converge to one line.** Justified as "nearly free today". Measured by the settings
session, then **re-taken by this session hours later and already moved**:

|                           | Their reading | Re-taken 2026-08-29 21:57 |
| ------------------------- | ------------- | ------------------------- |
| `print-fixes` ahead       | 4             | **5**                     |
| behind the main line      | 5             | **8**                     |
| **changed on BOTH sides** | **0**         | **0**                     |
| merge                     | clean         | **clean**                 |

**Only the third row is load-bearing.** Ahead and behind drift with every commit and cost nothing;
**zero files changed on both sides is what makes the merge free**, and the moment it is non-zero the
decision's justification is gone. Re-take before acting:

```bash
A=claude/ward-flow-print-fixes; B=claude/ward-flow-phases-6-7-design; M=$(git merge-base $A $B)
comm -12 <(git diff --name-only $M $A|sort) <(git diff --name-only $M $B|sort) | wc -l   # want 0
```

**The convention needed one more field, and PROC-3 is how we found out: record WHAT WAS MEASURED, not
only what the numbers were.** The re-take command above names `claude/ward-flow-print-fixes`. That
happens to be right — but this session reached that name by inheriting it from another session's
report, not by asking a worktree, and the ownership registry said something different. **A re-take
command that names a branch inherits every assumption in that name**, so running it tomorrow could
return a perfectly healthy number about the wrong branch, and the row would read as valid
indefinitely. The convention now requires the _subject_ to be re-verified, not just the number:

```bash
git -C <worktree> rev-parse --abbrev-ref HEAD    # ask the worktree, do not infer the branch
```

**And the sharpest form of it, which generalises past this project.** Every session held a warning
saying _"of the three `ward-board*` branches, only the unsuffixed one carries work"_. The live branch
was in none of that family — it is `claude/ward-flow-print-fixes`, named for a task that grew into
the board work and was never renamed. **A check phrased as "which of these is right?" cannot return
"none of them."** A question with a false premise returns a confident wrong answer and no error, and
every session that consulted that warning got one. The replacement is the only check that cannot be
wrong about itself: ask the worktree what branch it is on. _(Found by the fold session.)_

This is the same family as the prefix rule: **a justification that expires through ordinary correct
work**, with nobody at fault and no signal at the moment it stops holding.
